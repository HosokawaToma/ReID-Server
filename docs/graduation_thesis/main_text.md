# 2 システムの概要

## 2.1 全体像

本研究では，大学建物内における人の移動を，カメラ画像情報に基づいて継続的に把握することを目的として，人流解析システムを構築した．
システムでは，「カメラ画像の収集」「人物の検出」「人物画像の品質チェック」「人物の再同定（ReID）」「移動情報としての集計・検索」という一連の流れで，大学建物内の人流を解析する．

## 2.2 サーバ構成

本システムは，外部からのカメラ画像投入と分析結果の参照を行うための WebAPI サーバを中心に構成される．
カメラ画像から，人物の検出，品質チェック，再同定を行う処理は WebAPI の処理プロセスとは切り離して行う．
これにより，人物の検出と再同定の処理のワーカー数の調整や計算分散が容易になり，システムの拡張性が向上する．

人物の再同定（ReID）のために，人物の特徴量が含まれたベクトルデータとそれに紐づく時刻情報，カメラID，人物IDを保存する必要がある．
そのため，DBにはベクトル型のデータ形式を保存できるRDBが適している．
本システムでは，PostgreSQLにpgvectorを使用してベクトル型のデータ形式を保存する．

## 2.3 一連の処理

本節では，本研究で用いる一連の処理の流れを概説する．

### 2.3.1 カメラ画像の収集

各カメラ端末から取得した画像、カメラID、および撮影時刻を WebAPI を利用しサーバへ集約する．

### 2.3.2 人物の検出

人物の再同定には，人物が一人だけ写った人物画像が必要となる．
そのため，カメラの全域画像から人物領域のみを推定する必要がある．
本研究では，YOLOを利用しこれを行う．

### 2.3.3 人物画像の品質チェック

人物の再同定に用いる人物画像は，「一人だけが全身が写った鮮明な画像」のみにしなければ精度が大幅に落ちてしまう．
例えば，体の一部が隠れた画像を使用してしまうと，体の一部が隠れたという特徴を含んでしまい，同じ人物であるのにも関わらず特徴量の一致率が低下してしまい，精度が落ちてしまう．
他には，二人以上が写った画像を使用してしまうと，二人の特徴が含まれてしまい，一つの人物IDを二人が共有してしまい，結果的に全体の精度が落ちてしまう．
実際，有名なデータセットである Market1501 では，全身が写っていない人物画像や複数人が写っている人物画像は「ジャンクデータ」と設定しており，評価時にはこれを省く必要がある．
ジャンクデータを省かず評価を行ってしまうと，結果が悪くなってしまう．
Market1501 などのデータセットでは，事前にジャンクデータかどうかラベリングされているが，実環境ではラベリングを行う必要がある．
本研究では，「全身が写っていない人物画像」と「複数人が写っている人物画像」を「ジャンクデータ」と判定する．
これには，YOLOを用いることで，高精度で判定を行うことができる．

YOLOの個体識別モデルを用いて，画像内の人物数を推定し，単独の人物が写る画像のみを選別する．
YOLOの姿勢推定モデルを用いて，画像内の人物の姿勢を推定し，全身が写っている画像のみを選別する．

### 2.3.4 人物の再同定

人物再同定にはCLIP-ReIDを用い、抽出された特徴量と、同日に撮影された蓄積済みの全特徴量との照合を行う。最大類似度が閾値を上回る場合、該当する人物IDを対象画像へ割り当てる。一方、類似度が閾値に満たない場合は、新規の人物とみなし新たな人物IDを付与する。
