# 開発ルール

## 1. 機能要件を満たす

### 1.1. 仕様通りの振る舞いをする
- 正常系だけでなく、準正常系・異常系も仕様通りであること
- エッジケース（境界値）での動作確認がされていること
- 既存機能への影響（デグレ）がないか

## 2. 非機能要件を満たす

### 2.1. 機密性を確保する
- 適切な権限チェックが漏れなく実装され、未認証者や権限を持たないユーザーによるデータ閲覧・操作（IDOR等）が不可能であること
- パスワード、APIキー、個人情報（PII）がコードやログに平文でハードコーディングされていないこと
- ログ出力時に機密情報がマスクされており、ログからの情報漏洩リスクがないこと

### 2.2. 完全性を確保する
- トランザクション制御により、一連の処理が全て成功するか、失敗時に完全にロールバックされる（原子性）こと
- 同時更新時にデータが不整合を起こさないよう、適切なロック機構（楽観ロック/悲観ロック）が実装されていること
- 外部からの入力値に対し厳格なバリデーションを行い、不正な形式のデータがシステム内に混入しないこと
- 意図しないリクエストによるデータの書き換えや削除が防止されていること

### 2.3. 可用性を確保する
- N+1問題を回避し、DBアクセスが最適化されていること
- インデックスが適切に設定され、フルスキャンによる遅延がないこと
- 計算量が爆発するアルゴリズム（不要な多重ループ等）が含まれていないこと
- メモリリーク、DB接続やファイルハンドルの解放忘れがなく、長時間稼働してもリソースが枯渇しないこと
- 期せぬエラーが発生してもプロセス自体がクラッシュせず、エラーを検知・通知（ログ出力）した上で、可能な限りサービスを継続できること
- 障害発生時に迅速な復旧ができるよう、必要な調査情報（いつ・誰が・何を・エラー内容）がログに出力されていること

### 2.4. 保守性を確保する

- コーディング規約に従う
- オブジェクト指向で記述する
  - 単一責任の原則を満たしている（SOLID原則 - SRP）
  - オープン・クローズドの原則を満たしている（SOLID原則 - OCP）
  - リスコフの置換原則を満たしている（SOLID原則 - LSP）
  - インターフェース分離の原則を満たしている（SOLID原則 - ISP）
  - 依存性逆転の原則を満たしている（SOLID原則 - DIP）
  - 関心事が分散していない（DRY原則）
  - 現在不要な機能や過剰な抽象化が含まれていない（YAGNI原則）
  - 単純性を維持している（KISS原則）
  - オブジェクトに対し宣言的である（Tell, Don't Ask）
  - 最小知識の原則を満たしている（LoD）
  - 関数の抽象化レベルが揃っている（SLAP）
- テストコードを実装する
  - 主要なロジック分岐（C1）および境界値条件がテストコードによって網羅されていること
  - 各テストケースが他のテスト結果や実行順序に依存せず、単体で成功すること
  - 外部APIや現在時刻などに依存せず、いつどこで実行しても同じ結果になるようモック化されていること
  - テストコード自体が「仕様（どのような入力でどうなるべきか）」を説明するドキュメントとして読めること
